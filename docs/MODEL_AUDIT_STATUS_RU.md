# Статус аудита модели Caramba

## Что уже безопасно использовать

- контейнер CSM1 проверяется структурно;
- подпись Ed25519 проверяется до расшифровки;
- payload расшифровывается ChaCha20-Poly1305 с заголовком как AAD;
- Zstandard распаковывается только в пределах `plain_size`;
- SHA-256 проверяется до установки;
- кэш заменяется атомарно, предыдущая валидная версия сохраняется для rollback;
- DAWG-переходы проверяются на выход за границы.

## Что пока не считается доказанным

Сам факт достижения состояния DAWG ещё не означает, что это принятое слово.
В восстановленном бинарнике пока не подтверждены:

1. бит окончания слова;
2. порядок чтения букв (прямой или обратный);
3. принадлежность блока A к русскому или английскому языку;
4. смысл дополнительных флагов и весов.

Поэтому блоки не подключены к автоматической замене. Это предотвращает
ситуацию, когда случайный путь в графе превращается в неправильную замену.

Независимое исследование подтвердило, что это автоматы сопоставления
шаблонов, а не обычные RU/EN-словари: в графах есть циклы и output-link.
Флаг `0x100` означает наличие результата сопоставления. Из состояния
вычисляется непрозрачный `outputId`, который затем связывается с таблицей
правил. `outputId` нельзя считать словом, заменой или оценкой уверенности.

В SmartInput уже реализовано безопасное получение этого ID, но расшифровка
таблиц правил и полный путь `outputId → rule → решение` ещё не завершены.

## Реализованный режим audit-only

`RecoveredRulePack` читает версию из manifest, сверяет SHA-256 обоих
автоматов одновременно с `hashes.sha256`, сохраняет все raw/opaque поля и
предоставляет только следующие операции:

```text
Match(A|B, preparedBytes) → source + opaque outputId + byte offset
TryResolveRule(A|B, outputId) → opaque raw record + SHA-256 этой записи
AuditOpaqueBindings() → соответствие reachable ID и таблиц без текста
```

Для подтверждённой native-механики добавлен отдельный вызов
`MatchSubstrings(A|B, Forward|Reverse, preparedBytes)`: он запускает state 0
на каждом байтовом смещении вперёд либо на каждом окончании назад и возвращает
все найденные opaque ID. Это повторяет только matcher-циклы; нормализация,
границы слова и classifier по-прежнему не угадываются.

Boundary-аудит также возвращает RVA выбранного статического descriptor
(`0x81D538` или `0x81D53E`). Это именно данные, которые передаются общей
функции transform `0x39C20`, а не адрес callback-функции. Результат и байты
после `0x39C20` пока считаются opaque.

Follow-up-анализ подтвердил дополнительную структурную связь B:
`outputId → group-5.field-2.field3 → group-5.field-3[index]`. В адаптере есть
`TryResolveBLinkedRecord`, который проверяет диапазон и возвращает обе записи
как opaque bytes. Это не декодер replacement и не разрешение на live-замену.

Последующий static-анализ уточнил transform: `0x39C20` создаёт owned 24-byte
буфер совместимого с Rust layout `{capacity, pointer, length}` и делегирует
запись descriptor-driven writer `0x82F70`. В SmartInput сохранены только
структурные константы этого layout и descriptor bytes; операции `0x82F70`
на descriptor opcode пока неизвестны и намеренно не воспроизводятся.

После reverse collection подтверждён размер match record 32 байта и чтение
opaque `u32` по offset `0x18` в таблицу 16-byte entries. Связь этой runtime
таблицы с экспортированными rule-файлами не доказана, поэтому candidate и
classifier остаются отключёнными.

Вызов `AuditOpaqueBindings()` намеренно является тяжёлой offline-проверкой и
не используется в keyboard hook. `Match` получает уже подготовленные байты:
preprocessor старой программы пока не восстановлен, поэтому результат
матчинга ничего не говорит о слове, языке, replacement или confidence.

Ни окно приложения, ни hook, ни `SendInput`, ни текущая автокоррекция не
зависят от этого пакета. Любая ошибка проверки целостности прекращает загрузку
до разбора бинарных данных.

## Пунктуация — отдельный preview

Смысловая пунктуация не связана с rule-pack. Добавлен чистый контракт
`IPunctuationProvider` и `PunctuationPreviewService`: provider может вернуть
только знаки после токенов и вероятность, сервис отфильтровывает небезопасный
ввод и формирует обратимую карту вставок. Пока установлен `NullPunctuationProvider`,
то есть приложение само ничего не меняет. Теперь для ручной страницы выбран
маленький детерминированный `RuleBasedPunctuationProvider`: он предлагает
только точку/вопросительный знак в конце и запятые перед ограниченным набором
союзов. Это baseline, а не «полная грамматика»; он не вызывается из hook.
Страница «Проверка пунктуации» позволяет явно проверить, применить только в
этом окне и отменить preview одной операцией. Тройной Shift не используется.

```powershell
  "C:\Users\shuly\Desktop\CarambaSwitcher-Recovery-Package-2026-09-05\model\latest-rules-decoded.bin" `
  src\SmartInput.Core\Dictionaries\Lexicons\ru_50k.csv `
  src\SmartInput.Core\Dictionaries\Lexicons\en_50k.txt
```

Скрипт выводит только агрегированные числа: количество проверенных слов,
достигнутых путей и совпадения по битовым гипотезам. Он не пишет слова в
отчёты и не читает пользовательский ввод.

## Условие подключения

Сначала нужен контрольный набор слов, для которого подтверждены ожидаемые
решения, затем отдельный тест терминального бита и RU/EN-блока. После этого
модель подключается сначала в `audit-only`, где она только формирует решение,
а текст изменяется только после сравнения с текущим движком.
