## Главная цель

Восстановить доказанную цепочку:

```text
наблюдение клавиш / текстовый буфер
  → preprocessor
  → подготовленные байты для автомата A и/или B
  → переходы / output-link
  → outputId
  → запись правила
  → classifier / policy
  → решение (ничего не делать | suggestion | layout | spelling | другое)
  → безопасное применение и Undo
```

Нельзя обозначать этап как восстановленный, пока нет минимум трёх независимых
синтетических примеров, которые проходят всю цепочку и совпадают с поведением
оригинального приложения.

## Что именно нужно исследовать

### 1. Точки входа и реальный call graph

Найди в EXE/DLL:

1. обработчик набора текста / границы слова;
2. место, где вызываются оба автомата;
3. функции подготовки входного буфера;
4. чтение `top.2.field.3`, `top.5.field.2`, `top.5.field.3` и auxiliary-блока;
5. классификатор, выбирающий финальное решение;
6. место, где решение передаётся в замену текста;
7. проверку безопасного контекста: password/secure field, terminal/IDE,
   исключённые приложения, URL/email/path/code, emergency pause и настройки.

Для каждого узла дай: модуль, адрес/символ/сигнатуру, псевдокод, кто вызывает и
кого он вызывает. Отметь, что доказано статически, динамически и только
предполагается.

### 2. Preprocessor — самый важный блок

Нужно установить точный формат входа каждого автомата:

- источник: клавиши, Unicode-текст, scan code, layout ID, внутренний буфер или
  иной объект;
- кодировка: UTF-16/UTF-8/ANSI/собственная таблица/байтовые классы;
- направление: прямое, обратное, по подстрокам, оконное, с restart/fallback;
- нормализация: регистр, `е/ё`, диакритика, повторные буквы, физическая
  RU↔EN-конвертация, Unicode normalization;
- добавляемые begin/end/boundary-маркеры и их байтовые значения;
- максимальная длина буфера, очистка на пробеле/пунктуации/смене окна;
- как обрабатываются пробелы, цифры, пунктуация, URL, email, пути, код,
  смешанная кириллица/латиница;
- вызываются ли A и B последовательно, параллельно либо в разных режимах;
- что делают промах, output-link, несколько output-link, циклы и fallback.

Требуются конкретные таблицы:

```text
синтетический вход → нормализованный буфер → точные bytes A/B → состояния → outputId
```

Минимум 20 случаев: русские, английские, неверная раскладка RU→EN и EN→RU,
регистр, границы, повтор букв, один неверный символ, пробел, запятая, URL,
email, путь, identifier и mixed-script. Используй только искусственные строки,
а не пользовательский текст.

### 3. Таблицы правил и схема protobuf-подобных записей

Расшифруй, с byte-level доказательствами:

- `top.2.field.3` / `group-2-field-3.jsonl`: все поля, wire type, тип,
  обязательность и роль каждого поля; отдельно подтвердить, что field 1 — ID;
- `top.2.field.4`, `top.3.field.2`, `top.3.field.3`: связь с A, режимами или
  политиками; opaque-поля не выбрасывать;
- `top.5.field.2` / `group-5-field-2.jsonl`: полный schema, особенно поле,
  указывающее на `group-5-field-3`;
- `top.5.field.3` / `group-5-field-3.jsonl`: назначение 2 426 записей;
- точная индексация `0-based`/`1-based`, sentinel/null record и поведение
  out-of-range;
- `auxiliary/group-3-field-2.bin`: формат, размер блоков, таблицы/флаги;
- `special-app-behavior.raw.json`: только как исследовательский источник —
  нужно сопоставить с реальными safety-проверками, не переносить вслепую.

Для каждого поля подготовь таблицу:

| Артефакт / поле | Доказанная семантика | Доказательство | Неопределённость |
|---|---|---|---|

Не называй числовое поле confidence, language или replacement без трассы от
реального кода до влияния на финальное решение.

### 4. Classifier и правила выбора

Определи:

- как соединяются результаты A и B;
- как одна rule record превращается в `Wait`, `Apply`, layout switch,
  spell correction или suggestion;
- все пороги, веса, флаги, priority/tie-break и условные ветви;
- какие источники блокируют замену правильного слова;
- что именно запускает RU↔EN physical-layout conversion;
- как обрабатываются несколько кандидатов и пользовательская отмена;
- сохраняется ли контекст предложения, активное приложение, раскладка,
  предыдущая замена;
- какая информация нужна для корректного Double Shift Undo.

Нужны не только позитивные, но и негативные трассы: известное правильное слово,
двусмысленная опечатка, URL/email/path/code, пароль/secure field,
terminal/IDE/excluded application, emergency pause и выключенная защита.

### 5. Runtime experiments — только безопасные

Если есть возможность динамического анализа, построй изолированный harness:

- без глобального keyboard hook;
- без SendInput/clipboard и без записи в чужие окна;
- с синтетическими буферами и фейковым контекстом;
- без сетевых запросов;
- без записи исходных строк в постоянные логи.

Разрешены debug-дампы структур, адресов и хэшированных ID. Если для отчёта
нужны строки — используй только заранее заданные синтетические тестовые строки.
Для каждого вывода приложи минимальный воспроизводимый эксперимент и его
результат.

### 6. Результат для интеграции в SmartInput

Подготовь чистую спецификацию и, если возможно, изолированный код без Win32:

```text
Prepare(input, context) -> PreparedInput
Match(prepared) -> opaque output IDs
Resolve(ids) -> opaque rule records
Classify(prepared, records, context) -> typed decision
```

Требования к будущей реализации:

- Core не зависит от Win32, hook или SendInput;
- модель не вызывает API ввода;
- финальное применение проходит через существующую транзакционную замену и
  существующий Double Shift Undo;
- URL, email, путь, код, смешанный алфавит, secure input, Safe Mode,
  excluded apps, emergency pause и Protection OFF всегда блокируют применение;
- нет сетевой отправки текста и нет текстовых диагностических логов;
- явный `Wait` при недоказанной либо неоднозначной семантике.

## Критерии готовности и формат ответа

Верни отчёт в следующем порядке:

1. **Краткий verdict:** что точно восстановлено, что нет.
2. **Call graph** с адресами/символами и псевдокодом.
3. **Полная спецификация preprocessor** с таблицей synthetic input → bytes → ID.
4. **Схема всех rule tables**, включая opaque-поля.
5. **Правила classifier** и порядок приоритетов.
6. **Минимальный безопасный API** для SmartInput.
7. **Набор тестовых fixtures** и expected results.
8. **Список рисков/неизвестного** и что нужно исследовать далее.

Строго разделяй пометки:

```text
CONFIRMED — доказано кодом или повторяемым экспериментом
LIKELY — сильная, но ещё не полная гипотеза
UNKNOWN — доказательств недостаточно
```

Не предлагай подключать recovered rules к live-автозамене, пока не будет
подтверждён весь путь `preprocessor → outputId → rule → decision` и пройдены
безопасностные тесты.
